# 异常处理重构记录

## 背景

原 `UserServiceImpl` 的异常处理存在以下问题：

- 各方法 try-catch 策略不统一，有的吞异常、有的透传 `e.getMessage()` 给前端（存在安全隐患）
- 业务错误（账号重复、用户不存在）和系统错误（数据库异常）混在一起处理
- `register` 方法在 `@Transactional` 下 catch 后直接 return，导致事务不回滚
- `login` / `whoami` 缺少事务，`updateLastLoginAt` 失败时数据不一致
- `updateUserInfo` 未返回更新后的数据，未处理全空请求体，rows == 0 风格与其他方法不一致
- 并发注册触发数据库唯一约束时，全局处理器直接返回 500

---

## 改造原则

1. **系统级异常**（数据库连接失败、空指针等）：不在 Service 层捕获，直接上抛，由全局处理器统一返回友好提示并记录日志
2. **业务预期错误**（账号重复、用户不存在、密码错误等）：抛出 `BusinessException`，由全局处理器转换为对应错误响应
3. **局部清理场景**：只在需要补偿操作时使用 try-catch，catch 后执行清理再重新抛出

---

## 新增文件

### `BusinessException.java`

```java
public class BusinessException extends RuntimeException {
    private final int code;

    public BusinessException(int code, String message) { ... }

    /** 默认使用 400 错误码 */
    public BusinessException(String message) { this(400, message); }
}
```

- 继承 `RuntimeException`，不需要显式声明 throws
- 携带 `code` 字段，支持自定义错误码，默认 400
- 由全局处理器捕获，不会触发 `@Transactional` 回滚（RuntimeException 默认回滚，需注意业务场景）

## 修改文件

### `ParamExceptionHandler.java`

新增两个处理器，并修改兜底处理器：

| 处理器 | 捕获异常 | 响应码 | 说明 |
|--------|----------|--------|------|
| `handleBusinessException` | `BusinessException` | 业务自定义 code | 直接返回业务错误消息 |
| `handleDataIntegrityViolation` | `DataIntegrityViolationException` | 409 | 并发写入触发数据库唯一约束时的友好提示 |
| `handleException`（修改） | `Exception` | 500 | 加了 `log.error` 记录日志，不再透传 `e.getMessage()` |

```java
@ExceptionHandler(BusinessException.class)
public ApiResponse<Void> handleBusinessException(BusinessException ex) {
    return ApiResponse.error(ex.getCode(), ex.getMessage());
}

@ExceptionHandler(DataIntegrityViolationException.class)
public ApiResponse<Void> handleDataIntegrityViolation(DataIntegrityViolationException ex) {
    log.warn("数据唯一约束冲突", ex);
    return ApiResponse.error(HttpStatus.CONFLICT.value(), "操作失败，数据已存在，请勿重复提交");
}

@ExceptionHandler(Exception.class)
public ApiResponse<Void> handleException(Exception ex) {
    log.error("系统异常", ex);
    return ApiResponse.error(HttpStatus.INTERNAL_SERVER_ERROR.value(), "服务器内部错误，请稍后再试");
}
```

| 业务错误处理 | `return ApiResponseUtil.error(...)` | `throw new BusinessException(...)` |

#### whoami

| 改动 | 原代码 | 新代码 |
|------|--------|--------|
| 事务 | 无 `@Transactional` | 加 `@Transactional(rollbackFor = Exception.class)` |
| 异常处理 | try-catch 吞异常，无日志 | 去掉 try-catch，异常自然上抛 |

#### getUserInfo

| 改动 | 原代码 | 新代码 |
|------|--------|--------|
| 业务错误处理 | `return ApiResponseUtil.error("用户不存在")` | `throw new BusinessException("用户不存在")` |

| 改动 | 原代码 | 新代码 |
|------|--------|--------|
| 空请求体校验 | 无，全空时 rows == 0 触发 | 提前校验，`throw new BusinessException("请至少提供一个需要更新的字段")` |

## 异常处理流程（改造后）

```
请求进入 Controller
    ↓
Service 执行业务逻辑
    ├─ 业务预期错误 → throw BusinessException → 全局处理器返回 400 + 业务消息
    ├─ 并发写入冲突 → DataIntegrityViolationException → 全局处理器返回 409 + 友好提示
    ├─ 参数校验失败 → MethodArgumentNotValidException → 全局处理器返回 400 + 字段错误详情
    └─ 系统异常     → Exception → 全局处理器记录日志，返回 500 + 友好提示（不暴露内部信息）
```

---

## 注意事项

- `BusinessException` 继承 `RuntimeException`，在 `@Transactional` 方法中抛出会触发回滚，这是预期行为（业务校验失败不应提交事务）
- 并发注册场景：check-then-act 竞态条件无法完全通过应用层消除，数据库唯一约束是最终保障，`DataIntegrityViolationException` 处理器负责将其转换为友好响应
- `updateUserInfo` 更新后的二次查库会增加一次数据库 IO，如果性能敏感可改为直接从 `request` 构建返回值（但需确保字段完整）
